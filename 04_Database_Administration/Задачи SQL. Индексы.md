## 📖 Кратко об индексах

Индекс — это дополнительная структура данных, которая помогает MySQL быстрее находить записи в таблице.

В MySQL 8.4 для обычных индексов InnoDB используется структура **B-Tree** — сбалансированное дерево поиска.

Упрощённо: вместо последовательного просмотра всех записей MySQL может перейти к нужной части индекса и найти подходящие значения.

Однако наличие индекса ещё не означает, что запрос обязательно выполнится быстрее.

### На что обратить внимание

**1. Запрос без подходящего индекса**

MySQL может просматривать всю таблицу, чтобы найти необходимые записи. В плане выполнения это часто отображается как полный просмотр таблицы.

**2. Запрос с подходящим индексом**

MySQL может использовать индекс для поиска нужных записей и сократить количество просматриваемых строк.

**3. Запрос с неподходящим индексом**

Индекс может существовать, но не подходить под условия запроса. Например, порядок столбцов в составном индексе имеет значение.

**4. Селективность поля**

Селективность показывает, насколько хорошо поле позволяет различать записи.

- Высокая селективность — много различных значений, мало повторений.
- Низкая селективность — мало различных значений, много повторений.

Например, поле с фамилией может иметь меньше различных значений, чем поле с номером документа. Но это необходимо проверять на реальных данных.

**5. Индекс не всегда ускоряет запрос**

Если запросу требуется большая часть записей таблицы, MySQL может решить, что полный просмотр таблицы эффективнее использования индекса.

## 🛠️ Как выполнять задания

Для каждого задания используется следующий алгоритм.

### Шаг 1. Выполнить запрос без дополнительного индекса

- Выполнить SQL-запрос.
- Зафиксировать время выполнения.
- Выполнить `EXPLAIN ANALYZE`.
- Изучить план выполнения.

### Шаг 2. Создать индекс

- Создать индекс, указанный в подсказке.
- Повторно выполнить SQL-запрос.
- Зафиксировать время выполнения.
- Выполнить `EXPLAIN ANALYZE`.
- Сравнить результаты с исходным вариантом.

### Шаг 3. Сделать вывод

Обратить внимание на:
- изменился ли способ доступа к данным;
- использует ли MySQL созданный индекс;
- сколько строк фактически обработано;
- изменилось ли время выполнения;
- появилась ли дополнительная сортировка.

**Важно!** `EXPLAIN ANALYZE` не просто показывает предполагаемый план — он действительно выполняет запрос и показывает фактическое выполнение.

В выводе `EXPLAIN ANALYZE` обращайте внимание на:
- `actual time` — фактическое время выполнения операции;
- `rows` — фактическое количество строк, возвращённых операцией;
- `loops` — количество повторений операции;
- название операции — например, `Table scan`, `Index lookup`, `Index range scan`, `Sort`.

Для дополнительной информации о выбранном индексе и типе доступа можно также выполнить обычный `EXPLAIN`.

**Выбрать всех сотрудников с серией паспорта 1015 и номером 542828.**


### Этап 1. Без дополнительного индекса

Сначала необходимо определить, какое из двух полей имеет более низкую селективность.

Для этого можно сравнить количество различных значений:

```sql
SELECT
    COUNT(DISTINCT series) AS unique_series,
    COUNT(DISTINCT number) AS unique_number
FROM workers;
```

Поле с меньшим количеством различных значений относительно общего количества записей имеет более низкую селективность.

Создайте составной индекс, расположив поле с низкой селективностью первым:

```sql

ON workers(number, series);
```

Выполните исходный запрос, зафиксируйте время и выполните `EXPLAIN ANALYZE`.

### Этап 3. Составной индекс с высокой селективностью первым

Удалите созданный индекс:

```sql
DROP INDEX idx_series_number ON workers;
```

Создайте индекс в обратном порядке:

```sql
CREATE INDEX idx_number_series
ON workers(series, number);
```

Повторите запрос и анализ выполнения.

Перед экспериментом проверьте соответствие исходного запроса структуре и данным таблицы. ## Задание 2. Поиск по имени и дате рождения

**Найти всех сотрудников с именем Алексей, родившихся после 1 июля 1999 года.**

Исходный запрос:

```sql
SELECT *
FROM workers
WHERE first_name = 'Алексей'
  AND birthday > '1999-07-01';
```

### Этап 1. Без дополнительного индекса

2. Зафиксировать время выполнения.
3. Выполнить `EXPLAIN ANALYZE`.

### Этап 2. Составной индекс с низкой селективностью первым

Определите, какое поле имеет более низкую селективность.

Для сравнения можно использовать:

```sql
SELECT
    COUNT(DISTINCT first_name) AS unique_names,
    COUNT(DISTINCT birthday) AS unique_birthdays
FROM workers;
```

Создайте составной индекс, расположив поле с низкой селективностью первым.

Если низкую селективность имеет `first_name`, индекс будет выглядеть так:

```sql
CREATE INDEX idx_first_birthday
ON workers(first_name, birthday);
```

Если низкую селективность имеет `birthday`, поменяйте порядок полей:

```sql
CREATE INDEX idx_birthday_first
ON workers(birthday, first_name);
```

Выполните запрос, зафиксируйте время и выполните `EXPLAIN ANALYZE`.

### Этап 3. Составной индекс с высокой селективностью первым

Удалите созданный индекс и создайте составной индекс с обратным порядком полей.

Например, если на предыдущем этапе использовался:

```sql
CREATE INDEX idx_first_birthday
ON workers(first_name, birthday);
```

удалите его:

```sql
DROP INDEX idx_first_birthday ON workers;
```

Создайте обратный вариант:

```sql
CREATE INDEX idx_birthday_first
ON workers(birthday, first_name);
```

Повторите запрос и анализ выполнения.

### На что обратить внимание

- Какой порядок полей позволил эффективнее выполнить запрос?
- Сколько строк фактически обработано?
- Используется ли индекс для обоих условий?
- Появилась ли разница во времени выполнения?

**Важное замечание:** в этом запросе условие по `first_name` является условием равенства, а условие по `birthday` — диапазонным. Индекс `(first_name, birthday)` обычно лучше соответствует такой комбинации: сначала отбираются записи по имени, затем применяется диапазон дат.

Поэтому эксперимент с обратным порядком нужен для сравнения, а не для утверждения, что поле с самой высокой селективностью всегда должно стоять первым.

## 📊 Справка по EXPLAIN и EXPLAIN ANALYZE

Для изучения плана выполнения используйте:

```sql
EXPLAIN
SELECT *
FROM workers
WHERE first_name = 'Иван';
```

Для анализа фактического выполнения:

```sql
EXPLAIN ANALYZE
SELECT *
FROM workers
WHERE first_name = 'Иван';
```

### Ключевые показатели обычного EXPLAIN

| Показатель | Значение |
|---|---|
| `type` | Способ доступа к данным |
| `key` | Индекс, выбранный MySQL |
| `rows` | Оценка количества строк, которые MySQL предполагает просмотреть |
| `Extra` | Дополнительная информация о выполнении |

Основные значения `type`:

- `const` — поиск по первичному или уникальному индексу с константным значением, когда ожидается не более одной строки.
- `eq_ref` — поиск одной строки по уникальному индексу при соединении таблиц.
- `ref` — поиск по неуникальному индексу.
- `range` — поиск по диапазону индекса.
- `ALL` — полный просмотр таблицы.

`ALL` не всегда означает плохую производительность. Если запросу требуется большая часть таблицы, полный просмотр может оказаться эффективнее использования индекса.

### На что смотреть в EXPLAIN ANALYZE

В отличие от обычного `EXPLAIN`, команда `EXPLAIN ANALYZE` показывает фактическое выполнение запроса.

Обращайте внимание на:

- `actual time` — фактическое время выполнения операции;
- `rows` — количество строк, фактически обработанных или возвращённых операцией;
- `loops` — сколько раз выполнялась операция;
- `Table scan` — полный просмотр таблицы;
- `Index lookup` — поиск по индексу;
- `Index range scan` — просмотр диапазона индекса;
- `Sort` — операция сортировки.

### Что можно считать хорошим результатом?

- MySQL использует подходящий индекс.
- Количество обрабатываемых строк уменьшилось.
- Время выполнения запроса сократилось.
- Удалось избежать лишней сортировки или дополнительных операций.

Но не нужно оценивать запрос только по одному показателю. Например, `Using filesort` в обычном `EXPLAIN` или операция `Sort` в `EXPLAIN ANALYZE` не обязательно означают, что запрос выполняется медленно. Важно учитывать весь план и фактическое время.

## 🛠️ Шпаргалка по работе с индексами

### Просмотр индексов таблицы

```sql
SHOW INDEX FROM workers;

-- Альтернативная команда
SHOW KEYS FROM workers;
```

### Создание индексов

```sql
-- Простой индекс
CREATE INDEX idx_column
ON table_name(column_name);

-- Уникальный индекс
CREATE UNIQUE INDEX idx_unique_column
ON table_name(column_name);

-- Составной индекс
CREATE INDEX idx_multiple
ON table_name(col1, col2, col3);
```

### Удаление индекса

```sql
DROP INDEX index_name ON table_name;
```

### Проверка плана выполнения

```sql
EXPLAIN
SELECT *
FROM workers
WHERE first_name = 'Иван';
```

### Анализ фактического выполнения

```sql
EXPLAIN ANALYZE
SELECT *
FROM workers
WHERE first_name = 'Иван';
```

### Обновление статистики таблицы

```sql
ANALYZE TABLE workers;
```

Эта команда обновляет статистику, которую оптимизатор использует при выборе плана выполнения.

**Примечание:** `SHOW PROFILE` и `SHOW PROFILES` в MySQL 8.4 ещё доступны, но считаются устаревшими (deprecated). Для этой лабораторной работы используйте `EXPLAIN ANALYZE`.

Команды `userstat` и таблица `INFORMATION_SCHEMA.INDEX_STATISTICS` не относятся к стандартному функционалу MySQL Community 8.4, поэтому в данной работе не используются.
